# Устройство Berl Novella Engine

## Текущая версия: только новелла

```text
manager.bne + scene/*.bne
            │
            ▼
   ProjectLoader / SceneParser     загрузка, ссылки, компиляция
            │
            ▼
          Project                 настройки, ресурсы, скомпилированные сцены
            │
            ▼
           Story                  переменные, переходы, стек вызовов, состояние
        ┌───┴───────────┐
        ▼               ▼
   Wait / Event      SaveStore     проверяемый JSON-снимок, атомарная запись
        │
        ▼
       App                       ввод пользователя и часы
    ┌───┴────┐
    ▼        ▼
 Renderer   Audio                pygame-ce; представление и звук
```

### Модули

| Файл | Ответственность |
| --- | --- |
| `bne/project.py` | Читает менеджер, проверяет ресурсы и ссылки, собирает проект |
| `bne/syntax.py` | Строки, кавычки, комментарии, отступы, идентификаторы |
| `bne/parser.py` | Компилирует метки, условия и меню в линейные инструкции |
| `bne/expressions.py` | Разбор и ограниченный интерпретатор выражений, подстановки |
| `bne/model.py` | Структуры проекта, `SceneSpec`, инструкции и разрешение целей |
| `bne/runtime.py` | Виртуальная машина новеллы, без зависимости от pygame |
| `bne/saves.py` | JSON-снимки, валидация при загрузке, атомарные слоты |
| `bne/render.py` | Кэш ресурсов, переходы, разметка, страницы диалогов, кнопки |
| `bne/audio.py` | Музыка, эффекты, необязательное звуковое устройство |
| `bne/app.py` | Оконный цикл, управление, меню и сохранение/загрузка |
| `bne/__main__.py` | CLI, в том числе проверка без графики |

## Почему компиляция, а не выполнение текста по строкам

Условия и ветки меню превращаются в явные адреса переходов. Текущую позицию
однозначно задаёт `Frame(scene, pc)`. `call` кладёт адрес возврата в стек;
`return` достаёт его. Все адреса получаются из проверенных сценариев,
а не из Python-кода пользователя.

Это позволяет:

- сохраняться непосредственно на диалоге, выборе или паузе;
- возвращаться из поддиалога в другой файл;
- проверять цели переходов до открытия окна;
- тестировать историю без SDL и без имитации мыши;
- позже менять способ отображения диалога, не переписывая язык.

Переменные, фон, спрайты и музыка принадлежат `Story`, а не глобальным
переменным pygame. Конкретный дисплей и время печати текста — забота `App`.

## Интерфейс ядра

```python
from bne.project import load_project
from bne.runtime import Dialogue, Ended, Menu, Pause, Story

project = load_project("game")
story = Story(project)
story.start()

while not isinstance(story.waiting, Ended):
    waiting = story.waiting
    if isinstance(waiting, Dialogue):
        print(waiting.speaker or "Рассказчик", waiting.text)
        story.advance()
    elif isinstance(waiting, Menu):
        print([choice.text for choice in waiting.choices])
        story.choose(0)  # здесь хост получает решение пользователя
    elif isinstance(waiting, Pause):
        story.advance()  # настольный хост вместо этого учитывает таймер

    # Хост забирает события для аудио/переходов; этот пример их не отображает.
    story.drain_events()
```

Ожидания: `Dialogue`, `Menu`, `Pause`, `Ended`.
События: изменение изображения/переход, начало и остановка звука.
Ядро не спит и не ждёт нажатий клавиш — поэтому его легко тестировать.
`menu` нельзя продолжить через `advance()`: нужен явный `choose(index)`.

## Сохранения

В JSON попадают только скаляры и описания состояния. Ожидание хранит ссылку
на проверенную команду: при загрузке реплика или меню восстанавливаются из
скомпилированного сценария и переменных. Адреса, ресурсы, стек, типы и диапазоны
проверяются **до замены текущей истории**. Неудачная загрузка не меняет живую игру.

SHA-256 отпечаток менеджера и подключённых сценариев не позволяет случайно
загрузить позицию из другой редакции истории. Изменение только PNG/WAV не
инвалидирует сохранение. Формат имеет собственную версию, независимую от
версии пакета; при расширении состояния его можно явно мигрировать.

Данные сначала пишутся во временный файл в том же каталоге, затем выполняются
`fsync` и атомарный `os.replace`. Старый слот сохраняется при ошибке записи.
Музыка при загрузке начинается сначала; одноразовые эффекты не воспроизводятся заново.

## Граница будущего RPG-режима

Нужный сценарий развития:

```text
новелла → прогулка по карте → взаимодействие с NPC → новая сцена новеллы → обратно на карту
```

Что уже подготовлено:

- Один `game/manager.bne` как реестр и точка входа.
- Логические идентификаторы сцен, не привязанные к именам файлов.
- Отдельное поле `SceneSpec.mode` (`novel` сейчас, `rpg` зарезервирован).
- Отделённые компилятор, состояние истории, ввод, рендерер и сохранения.
- Общие переменные и диалоговое ядро, которое не требует собственного окна.
- `game/rpg.bne` как место для будущего формата настройки карт.

**Чего пока нет:** загрузчика RPG-карт, тайлового рендерера, коллизий,
движения игрока, NPC, полноценного маршрутизатора разных режимов и сохранения состояния карты.
Их нельзя включить одной строчкой: текущий загрузчик намеренно отклоняет `mode rpg`.

### Следующий этап

1. Определить формат карт и ресурсов в `rpg.bne`, не меняя уже работающий синтаксис диалогов.
2. Добавить отдельные `MapState`, загрузчик карты, тайловый рендерер и контроллер движения.
3. Ввести маршрутизатор режимов над `Story` и RPG-состоянием, а не добавлять ходьбу в парсер реплик.
4. На взаимодействии с NPC запускать сцену новеллы, сохраняя позицию игрока и состояние карты.
5. На завершении поддиалога возвращаться в ту же карту без её пересоздания.
6. Расширить версию JSON-сохранений общими флагами и состоянием каждой посещённой карты.

Таким образом, первая версия остаётся полноценной небольшой новеллой,
а дальнейшая RPG-часть не маскируется неподдерживаемыми псевдокомандами.

## Ограничения и безопасность

`.bne` — не Python: AST проверяется по белому списку и затем интерпретируется вручную.
Нет `eval`, `exec`, импорта, доступа к атрибутам, функциям или индексам.
Сохранения не используют `pickle`. Пути не могут покидать папку игры.
У вычислений, строк, глубины вложенности, стека и цикла исполнения есть ограничения.
Это не обещание безопасности произвольных сторонних двоичных PNG/аудиофайлов:
их декодируют pygame и SDL, как в других мультимедийных приложениях.

Тесты ядра используют временные проекты. Интеграционный тест проходит все
ветки демо и проверяет восстановление состояния на каждом ожидании.
Тесты интерфейса работают через `SDL_VIDEODRIVER=dummy` и `SDL_AUDIODRIVER=dummy`.
